1. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
This report delivers an exhaustive, read-only architectural, persistence, and
containerization audit for deploying the Homelab Dashboard & Service Launcher
application inside a Docker container on Linux (Debian).

Key Findings Summary:
- Architecture: Modern client-server web application featuring a React 19 Single
  Page Application (SPA) frontend and a Node.js 22 Express backend bundled via
  esbuild into a single CommonJS server distribution (dist/server.cjs).
- Database & Persistence: Uses a flat-file JSON document store with atomic
  writes and automated fallback backup (.bak). All application state, uploaded
  logos/documents, and archives reside under a single directory tree
  (/app/data), making persistent storage and backups straightforward.
- Offline Capability: 100% functional in isolated/air-gapped environments. No
  external runtime APIs, no cloud authentication, and no outbound network
  requests are made by the backend.
- Critical Security/State Risk: The server startup sequence in server/db.ts
  automatically re-hashes and overwrites the admin account password with the
  INITIAL_ADMIN_PASSWORD environment variable (default: "123") on every container
  restart, resetting any password changes made through the web UI unless the
  environment variable is explicitly configured in .env.
- Docker State Safety: The container correctly runs as non-root (user: node,
  UID/GID 1000). Named volumes survive standard container restarts and updates;
  however, executing "docker compose down -v" destroys named volumes. Using a
  host directory bind mount (e.g., /opt/homelab-data:/app/data) with proper UID
  permissions guarantees survival across all Docker teardown operations.


2. APPLICATION ARCHITECTURE
--------------------------------------------------------------------------------
Frontend Technology & Architecture:
- Framework: React 19.0.1 with TypeScript 5.8.2.
- Build Tool: Vite 6.2.3 using @vitejs/plugin-react and @tailwindcss/vite.
- Styling: Tailwind CSS v4 with custom Apple-inspired frosted glassmorphism
  utility tokens defined in src/index.css.
- UI Animation: Motion (motion/react v12.23.24) and canvas-confetti.
- Icons: lucide-react (v0.546.0) combined with a local, offline vector catalog of
  58 pre-compiled SVG homelab and Linux service icons (src/data/builtinIcons.ts).
- Typography: Local @fontsource/vazirmatn (v5.3.0) bundled into static assets,
  supplemented by Google Fonts link tags in index.html.
- State Management: React functional component hooks (useState, useEffect,
  useMemo, useCallback) synchronized with browser Web Storage and backend REST
  endpoints.

Backend / Server Technology & Architecture:
- Runtime: Node.js 22 (Alpine-based Linux in container).
- Framework: Express 4.21.2.
- Packaging / Bundling: esbuild 0.25.0 bundles server.ts and route modules into a
  single file (dist/server.cjs) with external package resolution.
- File Handling: Multer 2.2.0 for multipart file uploads with strict extension
  and MIME validation; adm-zip 0.6.1 for creating and extracting full ZIP
  system backups.
- Authentication: jsonwebtoken 9.0.3 for HMAC SHA256 JWT tokens and bcryptjs
  3.0.3 for salted password hashing.

API Structure & Communication:
- Communication between frontend and backend is conducted over a JSON REST API
  mounted at /api/*.
- Endpoints are partitioned into public configuration routes (/api/public/*),
  authentication routes (/api/auth/*), and admin-protected routes (/api/admin/*).
- Static uploaded files are served from /uploads/* with HTTP cache headers
  (max-age 86400, stale-while-revalidate 604800) and inline disposition.
- Unhandled /api/* routes are terminated with 404 JSON to prevent accidental SPA
  HTML fallback.

Runtime Entry Points:
- Development Entry Point: "npm run dev" -> "tsx server.ts" (Express with Vite
  middleware mode).
- Production Entry Point: "npm start" -> "node dist/server.cjs" (Serving compiled
  static files in dist/ and handling /api routes).

Build Process:
1. "vite build": Compiles React JSX/TSX into minified, hash-named bundles in
   dist/assets/ and copies static files to dist/.
2. "esbuild server.ts --bundle --platform=node --format=cjs --packages=external
   --sourcemap --outfile=dist/server.cjs": Compiles TypeScript backend files into
   a standalone CommonJS bundle.

Production Startup Process:
1. Docker container boots with "node dist/server.cjs" as user "node" (UID 1000).
2. Environment variables are loaded via dotenv/config and system process.env.
3. DatabaseService resolves DATA_DIR (from DATA_DIR env, .datadir, or ./data).
4. Auto-migration check: If an external DATA_DIR is newly configured and empty,
   it copies existing database and uploads from the local project data directory.
5. Loads and validates database.json; falls back to database.json.bak if corrupted.
6. Synchronizes default admin credentials via ensureDefaultUsers().
7. Express binds to 0.0.0.0:3000.
8. Registers OS process signal listeners (SIGTERM, SIGINT) for graceful shutdown.

5. DATA PERSISTENCE
--------------------------------------------------------------------------------
Persistence Strategy Assessment:
- All dynamic data strictly resides under a single parent directory defined by
  the environment variable DATA_DIR (defaulting to /app/data inside the container).
- The application implements an atomic file writing pattern:
    1. Write JSON to database.json.tmp
    2. Sync and rename database.json.tmp to database.json
    3. Replicate copy to database.json.bak
  This ensures that sudden container termination, power outages, or host reboots
  never leave database.json in a truncated or corrupted half-written state.
- Critical Data for Backup:
  1. database.json
  2. uploads/ directory
  3. .env configuration (containing JWT_SECRET)


6. DATABASE ANALYSIS
--------------------------------------------------------------------------------
Database Technology:
- Flat-file JSON Document Database managed by DatabaseService (server/db.ts).

Database Files:
- Primary file: /app/data/database.json
- Redundant mirror: /app/data/database.json.bak
- Visits file: /app/data/visits.json

Schema Definition:

- categories: Array of Category objects (id, name, icon, sortOrder, description).

  details).

Migration & Initialization Mechanism:
- If database.json does not exist:
  1. If DATA_DIR is an external path and local ./data/database.json exists, it
     automatically copies the existing local database and uploads directory.
  2. Otherwise, initializes with rich default homelab categories, sample
     services, default portal settings, and creates an initial admin user.
- Schema auto-repair: Missing schema fields in existing JSON files are populated
  with default values upon reading.
- Container Re-creation Loss Assessment:
  - If /app/data is mounted to a Docker Volume or Bind Mount: NO data loss occurs.
  - If /app/data is NOT mounted: DATA WILL BE LOST when the container is deleted.


7. DOCKER STORAGE
--------------------------------------------------------------------------------
Container Paths:
- /app: Working directory containing application code.
- /app/dist: Static frontend build and bundled server (Read-only at runtime).
- /app/data: Persistent storage mount point for database, uploads, and backups.
- /app/data/uploads: Subdirectory storing uploaded files.
- /app/data/backups: Subdirectory storing generated ZIP backup files.

Volume Declarations:
- Dockerfile line 43 declares: VOLUME ["/app/data"]
  This marks /app/data as a volume mount point. If a user runs the container
  without specifying a mount, Docker creates an anonymous volume.

Docker Compose Volume Configuration (docker-compose.yml):
- Configured with named volume:
    volumes:
      - homelab_data:/app/data
    volumes:
      homelab_data:
        driver: local
- Alternative host bind mount documented in compose file:
    volumes:
      - ./data:/app/data

Comparison of Docker Storage Options for this Application:
1. Container Filesystem (No Mount):
   - Storage location: Container writable layer (/var/lib/docker/overlay2/...).
   - Container restart: Data survives.
   - Container recreation (docker compose up -d): Data is LOST.
   - Container deletion (docker rm): Data is LOST.
   - Assessment: UNSUITABLE FOR PRODUCTION.

2. Docker Named Volume (homelab_data:/app/data):
   - Storage location: /var/lib/docker/volumes/homelab_data/_data on host.
   - Container restart: Data survives.
   - Container recreation: Data survives.
   - Container deletion: Data survives.
   - Image upgrade / rebuild: Data survives.
   - Host reboot: Data survives.
   - "docker compose down -v": Data is DESTROYED (the -v flag removes volumes).
   - Assessment: ACCEPTABLE, but requires caution with the "-v" flag.

3. Host Bind Mount (/opt/homelab-data:/app/data or ./data:/app/data):
   - Storage location: Dedicated directory on host filesystem.
   - Container restart: Data survives.
   - Container recreation: Data survives.
   - Container deletion: Data survives.
   - Image upgrade / rebuild: Data survives.
   - Host reboot: Data survives.
   - "docker compose down -v": Data SURVIVES (bind mounts are never removed by -v).
   - Host migration: Easily copied via tar or rsync.
   - Assessment: RECOMMENDED FOR PRODUCTION.

17. UPDATE AND DATA-LOSS RISKS
--------------------------------------------------------------------------------
Scenario Analysis:

1. "docker compose pull" -> NO RISK.
   Only downloads new image layers. Running containers and data are untouched.

2. "docker compose up -d" -> NO RISK (with proper mounts).
   Gracefully stops old container, attaches existing volume/bind mount to the
   new container, and starts execution.

3. "docker compose down" -> NO RISK.
   Stops and removes containers and network. Persistent volumes are untouched.

4. "docker compose down -v" -> CRITICAL DATA LOSS RISK (with Named Volumes).
   The "-v" flag explicitly instructs Docker to delete all named volumes declared
   in the compose file. If homelab_data is a named volume, ALL DATABASE ENTRIES,
   UPLOADED LOGOS, AND BACKUPS WILL BE PERMANENTLY ERASED.
   Mitigation: Use a Host Bind Mount (e.g., /opt/homelab-data:/app/data).

5. Password Reset on Restart -> IMPORTANT OPERATIONAL RISK.
   In server/db.ts (lines 599-603), ensureDefaultUsers() runs on every boot:
   If an administrator changes their password via the UI, and the container
   restarts, the code resets the password back to INITIAL_ADMIN_PASSWORD.
   Mitigation: Define INITIAL_ADMIN_PASSWORD in .env to match the intended
   permanent password.

21. CLASSIFIED FINDINGS
--------------------------------------------------------------------------------

CRITICAL FINDINGS:
1. [CONFIRMED] Password Reset on Container Restart:
   In server/db.ts (lines 599-603), ensureDefaultUsers() runs whenever the server
   starts. It matches the admin username and overwrites the passwordHash with
   INITIAL_ADMIN_PASSWORD (default: "123"). If an admin changes their password
   via the Web UI, any subsequent container restart will silently reset their
   password back to INITIAL_ADMIN_PASSWORD.
   Remediation: Set INITIAL_ADMIN_PASSWORD in .env to the desired permanent
   password.

2. [CONFIRMED] Data Loss Risk with "docker compose down -v":
   The default docker-compose.yml defines a named volume "homelab_data". If an
   administrator tears down the environment using "docker compose down -v",
   Docker permanently deletes the named volume and all database/upload data.
   Remediation: Use a host bind mount (e.g., /opt/homelab-data:/app/data).

IMPORTANT FINDINGS:
1. [CONFIRMED] Host Directory Permissions on Debian (UID 1000):
   The container drops root privileges and executes under user "node" (UID 1000,
   GID 1000). When using a host bind mount (/opt/homelab-data), if the directory
   is created by root with default 755 permissions, the container will encounter
   EACCES errors and fail to save database.json or uploads.
   Remediation: Execute "sudo chown -R 1000:1000 /opt/homelab-data" on the host.

2. [CONFIRMED] Unused Dependency in package.json:
   The package "@google/genai" is declared in package.json dependencies, but is
   not imported or utilized anywhere in the codebase. Removing it avoids
   unnecessary download time during image compilation.

3. [CONFIRMED] External Font Tags in index.html:
   index.html includes external link tags for Google Fonts (fonts.googleapis.com).
   While @fontsource/vazirmatn is bundled locally, in an isolated air-gapped
   network, client browsers will trigger harmless network timeout warnings for
   Google Fonts. Removing the link tags ensures completely clean offline loading.

OPTIONAL IMPROVEMENTS:
1. [LIKELY] Replace "CMD ["npm", "start"]" with "CMD ["node", "dist/server.cjs"]":
   Running Node directly as PID 1 (or with Docker "--init") enables cleaner OS
   process signal handling and instant response to SIGTERM shutdown signals.

2. [CONFIRMED] Frontend Dependency Pruning from Runner Stage:
   Packages like "xlsx", "canvas-confetti", and "motion" are bundled into the
   frontend assets during build. They are not needed by Node at runtime and can
   be moved to devDependencies to minimize image size.
